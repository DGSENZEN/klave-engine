# Klave Engine: Milestone 0: Production and Pilot Readiness

**Document type:** Engineering handoff / execution specification  
**Baseline:** `DGSENZEN/klave-engine`, `main`, commit `ee2c33014b27e16e28d4d5799f837e806607724c` (verified 2026-10-22)  
**Status:** Plan only. No code, production configuration, or customer data has been changed.  
**Priority:** P0, prerequisite to feature expansion and a paid pilot.  
**Target outcome:** An existing invited customer can finish one real estimating job, and the team can prove that the exact tested build can be deployed, backed up, restored, diagnosed, and rolled back without silently losing data.

## 0. Executive decision

Milestone 0 is **not** a rewrite. It completes operational and acceptance gaps in the already built pilot foundation, especially the unfinished recovery drill. Preserve Python/FastAPI + Next.js, the single EC2 API host, Vercel frontend, PostgreSQL users database, workspace-scoped SQLite/catalog data, the current processing job store, and immutable run artifacts. Do not add PDF ingestion, new detectors, AI features, billing, public signup, or a new queue during M0. There should be zero intentional changes to quantity algorithms, calculation formulas, reference prices, bid semantics, or export layouts.

**Completion requires evidence, not only green unit tests:** one green production release of the approved commit; a valid recoverable backup stored away from EC2; a completed clean-room restore and API/export check; a rehearsed failure/rollback; a private gold regression report; and at least one real, independently observed estimator journey with its outputs reviewed. Where no real-world evidence exists, mark the gate **PENDING**, never PASS.

## 2. Definition of done (release-blocking gates)

- [ ] **G0: Baseline.** Release candidate full SHA, dependency lock hashes, Docker image IDs/digests, environment topology (without secrets), and known issues recorded in `docs/pilot-release-record.md` or a private completed copy. Existing numerical fixtures unchanged.
- [ ] **G1: Test.** `make release-check ENV_FILE=/abs/path/to/synthetic.env` passes on an isolated runner with real PostgreSQL, Docker, Playwright, and production image builds. No skipped mandatory stage masquerades as passing. Latest GitHub Actions PR verification passes.
- [ ] **G2: Real drawings.** `make eval-gold` passes on the machine holding *all selected* private fixtures; unavailable datasets listed explicitly. At least one real project with independently verified quantities is reviewed; label `baseline` never presented as ground truth.
- [ ] **G3: Secure deployment.** One approved `main` release completes end-to-end, API `/ready` returns 200, Vercel promotes **after** API readiness and the public frontend responds. EC2 `.release-current`, API/container image, front-end deployment and commit recorded and consistent.
- [ ] **G4: Off-host backups.** At least one complete, checksum-verified backup is copied to a separate encrypted/controlled destination and fetched back for validation. The copy includes accounts, workspace catalogs, source drawing files, processing control and related artifacts.
- [ ] **G5: Recovery.** Automated clean-room drill restores a backup into **fresh owned scratch** PostgreSQL/data resources, logs in an existing account, verifies workspace isolation, checks project/drawing/catalog persistence and validates a real XLSX. Original resources untouched.
- [ ] **G6: Rollback.** Controlled candidate-failure drill demonstrates that failed backup or failed API readiness does not advance `.release-current`; old API remains or returns healthy. A cross-version revert is tested against matching pre-upgrade data where necessary. Never claim data migration rollback solely from image rollback.
- [ ] **G7: Customer workflow.** A newly invited real pilot participant can upload a supported drawing, interpret coverage/units, review and sign off, map/price, export XLSX and confirm whether it imports into their real OPUS/Neodata setup. Record time, assistance, failures, and acceptance. No invented value measurements.
- [ ] **G8: Operational handoff.** An operator other than the implementer can follow the runbook to diagnose a failed job, verify backup age, perform isolated restore, identify exact release, and make a go/no-go decision with no secret leaks.

**Hard stop:** no unattended paid customer onboarding until G1, G3, G4, G5 and data isolation/security checks in G7 are complete. Gold limitations or real-suite incompatibilities may require restricting explicitly supported project/format scope rather than misrepresenting success.

## 3. Work packages and PR sequence

### M0-01: Inventory, lock the baseline, and document operational risk (P0)

**Likely files:** new `docs/pilot-release-record.md`; `docs/cicd.md`, `docs/despliegue.md` only where outdated; optional `scripts/release_record.py` if a small deterministic collector is justified. No production mutations.

1. Inspect GitHub Action `39684018436` and exact failed step logs; distinguish connection timeout, DNS error, rejected host key, failed authentication, missing target path, EC2-side backup failure, or unhealthy API. Do not infer the root cause from a failed step name.
2. Record full `main` SHA, dependency versions, `uv.lock` and `apps/web/package-lock.json` SHA256, user-data storage paths/Compose project, approved API host/domain, currently deployed backend SHA (`.release-current`) and Vercel deployment identifier. Keep hostnames/private addresses and backup paths in the private release record if sensitive.
3. Run current synthetic release and note elapsed time, disk/memory headroom, outputs, test skips, fixture availability, and warnings. Read current CI as-is before editing.
4. Record a **coverage matrix**: unit tests, Playwright real-service journey, synthetic engine check, private gold, external customer acceptance, cloud release and restored data. The last three are not implied by the first three.
5. Freeze output expectations for a synthetic work sample and real fixtures. Explicitly note source classification (`engine` versus `human`/`crudo`) and current availability. Do not recapture baselines to hide failures.

**Acceptance:** reviewer can determine precisely what is proven vs unproven; record references immutable SHA and artifact IDs; no customer drawings/secrets committed.

### M0-02: Repair production release transport and prove deployment (P0)

**Likely files:** `.github/workflows/release-check.yml`, `deploy/ec2-release.sh`, `tests/test_ec2_release.py`, `docs/cicd.md`, `docs/ec2.md`; production network/IAM/security-group settings are operator-managed.

1. Collect safe redacted diagnostics: workflow failed command/error; `EC2_HOST` configuration existence; DNS resolution; instance state and stable IP; EC2 SG inbound SSH source; host firewall/routing; SSH server; and `EC2_KNOWN_HOSTS` fingerprint compared out-of-band with host. Confirm no private key material is included in logs.
2. **If CI runner IP is blocked:** do not open TCP/22 to the whole Internet or disable host-key verification. Choose an approved deploy transport: e.g. AWS Systems Manager with short-lived GitHub OIDC credentials, or a restricted runner/network path. Separate this choice into its own infra change with least privilege; do not attempt a blind SSH retry loop.
3. Make failure modes actionable but safe: transport preflight (no credentials printed), bounded timeout, clear stage names and `if: always()` credential cleanup. Preserve Vercel stage-before-API and promote-after-ready ordering.
4. Harden `ec2-release.sh` so deployment archives are unpacked into an isolated release directory or fully validated staging location, not partly over active source. Preserve `.env.prod`, existing volumes and old image IDs. Keep backup before API cutover and ensure candidate failure does not write `.release-current`.
5. Write regression tests for bad SHA, unreachable/denied transport (at workflow/integration layer when possible), bad archive, failed build, failed pre-upgrade backup, failed readiness, and interrupted release. Simulated shell tests are necessary but not sufficient for live deployment proof.
6. Run an operator-approved release of the already verified commit; record API `/ready` from internal host and public endpoint, published Vercel URL, released SHA, and post-promotion frontend response.

**Acceptance:** green deploy job and matching release fingerprint; a failed candidate cannot be reported as deployed; production uploads/drawings/catalogs preserved. No disabling network/auth controls to achieve green CI.

**Rollback:** preserve the last healthy API image and corresponding data snapshot; restore old image/Compose configuration. If schema/data changed incompatibly, perform reviewed restoration of its matching pre-change backup and explicitly acknowledge any post-snapshot data loss.

### M0-03: Implement isolated, executable recovery drill (P0)

**Likely files:** create `deploy/recovery_check.py`, `tests/test_recovery_check.py`; change `deploy/smoke.py`, `deploy/compose.smoke.yml`, `scripts/release_check.py`, `Makefile`, `docs/despliegue.md`, `deploy/backup.sh` only as necessary. Adapt Plan C3; do not create an unrelated backup system.

**Proposed CLI:** `uv run python deploy/recovery_check.py --state-dir /absolute/owned/smoke --backup /absolute/completed/stamp` (final exact interface may evolve with tests). The command must refuse unowned state and non-scratch targets.

Implement test-first:

1. Seed an isolated original environment: PostgreSQL admin/session/workspace/roles, project access, a workspace catalog item, price/alias, known synthetic DXF and reviewed/priced report. Use fixture hashes and canonical workbook cell expectations from `apps/web/e2e/check_workbook.py` and `expected.json`.
2. Quiesce writers for a consistent pre-upgrade snapshot; run the **real** backup image using `deploy/backup.py once`. Validate `COMPLETE`, manifests, checksums, PostgreSQL dump list and archive members. Capture stamp and source commit.
3. Create wholly new, uniquely named scratch database and scratch data volume/dir with ownership labels. Refuse existing or live targets. Never run `docker compose down -v` on the active `klave` Compose project.
4. Restore `users.dump` to scratch PostgreSQL 16 via `pg_restore --exit-on-error --no-owner --no-acl`; restore SQLite snapshots and ordinary files from `sqlite.tar.gz` and `data.tar.gz` only after validating archive member safety. Re-verify copied archives at the destination.
5. Start matching API image against **scratch** resources. Assert `/ready` 200, original account login, expected workspace/role and project access, matching drawing-file SHA256, matching catalog data, persisting reviews, and the presence/correct quantities/P.U./evidence of a downloaded XLSX. Compare canonical workbook cell values, not XLSX ZIP bytes or generated timestamps.
6. Inject failures: incomplete manifest, missing COMPLETE, altered checksum, malicious tar path/symlink, pre-existing destination, failed `pg_restore`, unavailable source, interrupted job and restart. Assert original application data/database/image unchanged and no success marker.
7. Implement cleanup confined to resources recorded in an owned state file; leave forensic information if cleanup fails but never remove unrelated resources. Run the drill twice from fresh state to prove isolation/repeatability.
8. Add a synthetic owned recovery stage to `make release-check`. Keep production backups and drawings **outside CI**. Add a separate documented operator drill for restoring a real off-host backup into private isolated resources.

**Acceptance:** one successful automated restore-and-export from actual backup archive; all safety/integrity negative tests pass; no customer data or production credentials in CI. Distinguish *archive integrity check* from *successful application restore*.

### M0-04: Off-host backup and restore operations (P0, operator-dependent)

**Likely files:** `deploy/backup.py`, `deploy/backup.sh`, `docs/despliegue.md`, `docs/ec2.md`, `docs/pilot-release-record.md`, optional `deploy/offsite_backup.sh` or narrowly scoped script. Do not introduce a cloud-provider dependency by default.

1. Operator selects separate destination (cloud object storage/backup service or separate controlled storage), permissions, encryption method, retention requirement, access policy, and alert recipient. Restrict write privileges; prefer encrypted, versioned/immutable copies where feasible. Repository must not contain destination keys or customer filenames in logs.
2. Upload only fully completed verified backups. Preserve all archive files, manifest, COMPLETE and source commit metadata. Verify SHA256 checksums *after transfer*; test pulling at least one backup back from the remote destination.
3. Store last successful offsite copy UTC time and checksum summary in a private operator state; alert for missed backup or copy/verification failure (initial operational threshold: more than 36 hours since last successful offsite copy, adjustable to chosen backup cadence). Confirm alerts reach an actual operator, not just a log line.
4. Document copy/restore flow, expected data loss window, key loss implications, rotation and expiration, capacity/disk monitoring, and selection of the **matching pre-upgrade snapshot** for old binaries. Run restored application verification under M0-03 in separate resources.
5. Ensure retention never deletes the only restorable off-host copy because a new backup failed. Schedule restore drills (initially each release for synthetic; periodic for real offsite backup) and record the last drill outcome.

**Acceptance:** completed restore from an off-host copy, with confidential data access controlled and verified, and a delivered alert when a simulated backup/copy failure occurs. Off-host path chosen and configured by operator; no secret values in public docs or CI artifacts.

### M0-05: Pin correctness and customer journey acceptance (P0)

**Likely files:** `apps/web/e2e/journey.spec.ts`, `entry.spec.ts`, `upload.spec.ts`, `check_workbook.py`, `tests/test_projects_api.py`, `tests/test_ec2_release.py`, appropriate `tests/test_*`, `docs/evals.md`, `docs/pilot-release-record.md`. Reuse fixtures and code paths.

1. Keep existing browser E2E journey (invitation → upload → processed → verification → mapping → export) as a mandatory gate. Do not duplicate the same scenario in a second test suite.
2. Add missing invariants as focused tests: uncertain drawing units cannot publish an authoritative monetary total; unknown P.U. remains visibly unknown rather than $0; a rejected upload does not double-create a project; processing failure retains the uploaded source and offers retry; stale/SSE-disconnected UI refetches server state; signed review survives a server restart/reprocess when evidence remains equivalent; cross-workspace access is denied for project artifacts and relevant read routes.
3. On private fixture-bearing infrastructure, run `make eval-gold`, `uv run python -m klave_engine.evals.compare ...` against at least one independent human estimate, and `recall_cli` for the families relevant to the pilot project. Report counts, quantities, misdetections, unmatched lines, unknown prices and human decision time. Keep uncertainty and coverage gaps visible.
4. Execute a representative **real DWG** on the actual converter build and a representative DXF; record converter details, sheet coverage and failures. A synthetic DXF alone does not prove production DWG conversion.
5. Customer session: invite someone not involved in implementation; let them start with the app URL and a prepared real project; no live coaching unless logging as an intervention. Observe successful delivery into existing estimating workflow. Ask them to import the XLSX in their actual OPUS/Neodata installation; save a redacted compatibility report. Manual human acceptance is not an automated CI gate.
6. Include small negative acceptance journeys: an unreadable/partial sheet, incorrect scale, no price, invalid invitation, and lost connection. These should fail safely and explain the next action, not fabricate quantities or expose data.

**Acceptance:** signed customer journey record, actual workbook inspected and externally tested, correctness discrepancies documented. Restrict advertised support to families/formats verified; do not require fixing every known detector limitation to complete Milestone 0 if clearly disclosed and outside pilot scope.

### M0-06: Observability, release operations and final go/no-go (P0)

**Likely files:** `docs/diagnostics.md`, `docs/cicd.md`, `docs/pilot-release-record.md`, optionally `tests/test_job_diagnostics.py`, `tests/test_diagnostics.py`, and operational checks. Extend rather than replace `apps/api/observability.py` and `jobs.py`.

1. Use existing `X-Request-Id`, job ID, run ID and sanitized workspace logs to follow one upload/process failure across HTTP response, worker lifecycle and persisted job record. Verify error detail is scoped to the originating workspace.
2. Add an operator runbook: relevant read-only inspection commands, distinguishing `/health` and `/ready`, diagnosis of PostgreSQL/volume/convert failures, known limitations, escalation, and the safe procedures for reprocessing a *saved* project. No broad log dump containing filenames/tokens.
3. Configure minimal external synthetic checks for public `/ready` and frontend welcome, alert delivery, and disk space/backup age checks. Any alert must be tested by simulating an isolated failure. Keep sensitive endpoint and credentials out of public artifacts.
4. Run a failure game day using synthetic/staging resources: disable scratch database, exhaust scratch writable space or mock permissions, interrupt running job, force backup failure, and reject candidate readiness. Verify operator can identify, contain, recover and document each incident.
5. Record release and rollback decisions, responsible reviewer, date, evidence links, pending items and acknowledged limitations; publish no production rollout if mandatory gates are red.

**Acceptance:** another developer/operator can follow a redacted support reference from failed operation to safe action, verify health and backups, and demonstrate a successful recovery without improvising production commands.

## 4. Dependency graph and execution order

`M0-01 baseline` → `M0-02 deploy transport` and `M0-03 recovery automation` in parallel → `M0-04 off-host recovery` → `M0-05 real workflow correctness` → `M0-06 handoff and release decision`.

M0-05 browser regression work may start in parallel with M0-02/M0-03, but live customer acceptance should wait for stable deployment, isolation and backup readiness. Pull requests remain individually reviewable; no mixed refactor/new-domain-feature PRs.

Suggested assignments: one backend/reliability engineer owns M0-03 and data invariants; one deployment/operator owner handles M0-02 and M0-04; product/QA leads M0-05; a technical reviewer not implementing the same work signs off M0-06. For one engineer, execute sequentially and have someone else review recovery/rollback safety.

Rough planning estimates (not promises): baseline/diagnosis 1–2 engineer-days; release path 2–5 depending on network solution; recovery drill 4–7; off-host automation 2–4 plus operator configuration; quality/pilot acceptance 3–6 plus customer availability; final runbook 1–2. Scope or time will increase if infrastructure access or real fixture availability is blocked.

## 5. Nonfunctional constraints

**Security:** Keep invite-only onboarding, authentication and workspace isolation intact. Never check in `.env.prod`, production tokens, SSH material, customer drawings or real backups. Do not disable `StrictHostKeyChecking` or expose database/API ports to the public. Production writes and restores need explicit operator approval. Sanitize diagnostics.

**Consistency:** Project processing produces immutable run artifacts; human decisions are durable control data and must survive retries. Never treat an HTTP `GET` as permission for costly or stateful recomputation. No quantity/price/cost-model changes during M0. When a drawing's scale or P.U. is unverified, the export/disclosure semantics stay the same.

**Operations:** One API process, bounded in-process processing queue, persistent Docker volumes and PostgreSQL 16 remain in place. Health vs readiness retain existing semantics. Real backups remain private, and no destructive test touches live `klave` volumes. Keep prior image, backup, and evidence until acceptance.

**Compatibility:** No new PDF support, new discipline, billing or native OPUS/Neodata format project during M0. Existing Excel exchange remains, but the pilot must explicitly test its acceptance in actual desktop software.

## 7. Tests to implement explicitly

| Test | Expected result |
|---|---|
| Archive missing COMPLETE / corrupted sha256 / unsafe tar member | Abort before restore, no resources mutated |
| Restore invoked with live or unowned data/DB target | Abort without touching original data |
